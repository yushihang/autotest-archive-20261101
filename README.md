# autotest

基于 AI 的自动测试工具：它自己读代码、自己想用例、自己跑，跑完了自己提 PR。

PR 里**只有测试**。业务代码一行都不改。

## 简介

### 一句话说清

给一个仓库，它还你一个能合并的测试 PR。

人不用写用例、不用挑断言、不用整理报告，只需要在 PR 上点 review。

### 它解决什么

不是「让 AI 帮我想几个测试」，而是这几件具体让人烦的事：

- **老项目没有测试**。想补，但从哪开始、补到什么程度、怎么保证补的不是废测试，没人愿意接这活。
- **需求改得快，回归测试追不上**。线上出问题才发现某条路径根本没覆盖。
- **写测试的成本高于它的收益**。一个人写一天，验证的东西五分钟就讲完了。
- **失败结果没人看**。CI 红了，报告一百行，最后谁也没读。

### 工作流程

```
        读取仓库               理解意图             规划用例
   ┌──────────────┐    ┌──────────────┐    ┌──────────────┐
   │ 代码结构      │───▶│ 这个模块做    │───▶│ 覆盖哪些行为  │
   │ 已有测试      │    │ 什么、边界在哪 │    │ 优先级排序    │
   │ 提交历史      │    └──────────────┘    └──────┬───────┘
   └──────────────┘                               │
                                                  ▼
        提 PR                 生成并跑通           沙箱执行
   ┌──────────────┐    ┌──────────────┐    ┌──────────────┐
   │ 只含测试文件  │◀───│ 用例写进代码  │◀───│ 隔离环境      │
   │ 附用例清单    │    │ 直到真的通过  │    │ 可重复、无外网 │
   └──────────────┘    └──────────────┘    └──────────────┘
```

1. **读取**：解析仓库结构、已有测试、最近的改动，判断哪些模块是「重要但没测」的。
2. **理解**：从代码、注释、文档、提交信息里推断这个模块该有的行为，而不是从函数名瞎猜。
3. **规划**：列出要覆盖的行为点和边界条件，排优先级。低价值的用例直接不写。
4. **执行**：在隔离环境里跑，结果必须可复现。
5. **生成**：把通过的用例落成测试代码，风格跟仓库现有测试保持一致。
6. **提 PR**：新分支、只加测试文件、PR 描述里写清楚覆盖了什么、为什么选这些。

### 边界（重要）

这是这个项目和「AI 修 bug」类工具的根本区别：

| 做 | 不做 |
|---|---|
| 新增测试文件 | 修改业务代码 |
| 补充已有测试文件里的用例 | 修改已有测试的断言 |
| 报告疑似 bug | 修复疑似 bug |
| 提 PR 等人 review | 自动合并 |

**工具发现的失败，不等于业务有 bug。**

测试红了只有三种可能：真有 bug、测试写错了、环境不对。判断责任在人，工具只负责把证据摆整齐——失败的输入、期望、实际的输出、可复现的最小步骤。

不做自动修复，也不做自动跳过。失败的用例在 PR 里明确标出来，交给写代码的人。

### 设计约束

这些不是可选项，破坏其中任何一条，产出就不可信：

- **可复现**。同一个用例跑两次结果必须一致。有随机性的地方要能固定种子。
- **幂等**。用例不能依赖执行顺序，不能互相污染状态。
- **不碰真实数据**。测试数据全部自造，禁止连生产库、禁止用真实用户信息。
- **零外网依赖**。外部服务必须 mock 或本地起，网络抖动不该让用例变红。
- **flaky 先归因再上报**。同一个用例重跑若干次，只有稳定失败才算失败；偶发失败单独归类，不混进结论。
- **有成本上限**。单次任务的时间、token、执行次数都要封顶，超了直接停并报告，不许无限试错。

### PR 规范

每个自动 PR 必须自带这些信息，reviewer 不看代码也能判断值不值得合：

- 标题：`test: 给 <模块> 补 <N> 条用例`
- 描述里包含：覆盖的行为点清单、没覆盖的部分及原因、失败的用例（如果有）及证据
- 每个用例对应它的意图，不能出现「为了覆盖率」而写的空断言
- 一次 PR 只做一件事，不混杂无关模块

### 权限与安全

- 用最小权限的 token：能建分支、能开 PR，不能直接推主分支
- 业务代码只读
- 目标仓库要开分支保护，自动 PR 必须走人工 review
- 执行环境与宿主机隔离，不挂载敏感目录

### 非目标

明确不做，免得范围无限膨胀：

- 不替代人工探索性测试
- 不做性能压测、不做安全渗透测试
- 不追求覆盖率数字本身，覆盖率只是副产物
- 不做「AI 自己判断需求对不对」

### 常见问题

**会改我的业务代码吗？** 不会。PR 里只有测试文件，业务代码一行不动，发现的问题只报告、不修复。

**单次任务有运行时限吗？** 有。每一次任务都有硬性时间上限，到点即停，已跑通的用例照常提 PR，没跑完的部分在描述里写明停在哪一步、为什么停——不会为了「凑完整」而无限重试。

**单次任务的费用有上限吗？** 有。时间、token、执行次数各自封顶，换算成一个单次任务的预算上限，花到上限即停，不会为了「再试一次」继续烧钱。停下来时同样交 PR：已跑通的用例照常提，没跑完的部分写明停在哪一步、已经花掉多少、还差多少。

相关演示见 [docs/money-budget-demo.md](docs/money-budget-demo.md)：它验证的是失败会不会被如实上报，而不是预算拦截能力本身。

## 快速开始

> 当前为设计阶段，以下为目标用法；已经能跑的是配置校验（`npm test`），仓库里还有一个零依赖的演示靶子 [demo-app](demo-app/README.md)，见「现状」。

### 安装

**运行时要求：Node.js >=20**（低于 20 的版本无法运行，`package.json` 的 `engines.node` 也声明了这一点）。

克隆仓库即可获取本项目：`git clone <仓库地址>`。

拿到代码后：`npm install`，`npm test` 跑单元测试。直接依赖的版本已写死，但仓库还**没有提交 `package-lock.json`**——锁文件要由 `npm install` 生成，装好后请一并提交，否则「可复现」只覆盖直接依赖、传递依赖每次安装仍重解析。

### 试一试演示靶子

[demo-app/README.md](demo-app/README.md) 是一个零依赖 web 演示靶子（登录 + 待办）：

```bash
node demo-app/server.mjs
```

然后访问 http://127.0.0.1:4173 ，或直接打开 `demo-app/index.html`。

### 配置文件

配置文件（被测地址、成本上限、输出目录）的字段与校验规则见 [docs/config.md](docs/config.md)，完整示例见 `autotest.config.example.json`。

### 发起一次任务（目标用法）

1. **准备权限**：按「权限与安全」建一个最小权限 token——能建分支、能开 PR，不能直接推主分支；目标仓库开启分支保护，自动 PR 必须走人工 review。
2. **准备环境**：执行环境与宿主机隔离，业务代码只读，不挂载敏感目录。
3. **发起任务**：指向目标仓库，说明要补测试的范围。触发方式是命令行手动跑还是挂在 CI 里，尚未确定（见「现状」）。

跑完你会拿到一个新分支上的 PR：只有测试文件，加上覆盖了什么、为什么选这些。

## 开发

### 技术栈

- **运行时**：Node.js >=20（`package.json` 的 `engines.node` 已声明），原生 ESM（`.mjs`）。**没有编译步骤**——不引入 tsc / babel / 打包器，模块用 `node` 直接跑（CLI 入口还没写，现在还只有 `src/config.mjs`、`src/types.mjs` 两个模块）。
- **浏览器自动化**：Playwright，版本在 `package.json` 里写死精确版本号（不用 `^` / `~`）；测试侧用 `@playwright/test`。
- **类型**：不写 TypeScript。三个契约用 JSDoc `@typedef` 定在 `src/types.mjs`，编辑器里照样有补全，运行时零开销。
- **模块协作**：模块之间只交换 JSON——探测产出 `Inventory`，规划产出 `TestCase[]`，执行产出 `RunResult`。契约先定死，各模块才写得通。
- **测试**：`npm test` 跑 `tests/` 下的单元测试（`playwright test`，不开浏览器）。当前覆盖配置校验的所有错误分支和契约常量。

### 目录结构

- `src/`——运行时模块，当前有 `config.mjs`（配置加载与校验）和 `types.mjs`（共享契约）。
- `tests/`——单元测试。
- `demo-app/`——零依赖演示靶子（登录 + 待办）。
- `docs/`——[配置说明](docs/config.md)、[失败上报演示](docs/money-budget-demo.md)。
