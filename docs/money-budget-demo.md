# 预算演示（money budget demo）

这份演示用来验证「单次任务有成本上限」这条设计约束在失败场景下的表现：任务没跑通时，结果是否被如实上报，而不是被修饰成「看起来过了」。

| 项 | 值 |
|---|---|
| 所属 | issue #58（计划 `plan:e2e-cost-mvwbb3zk` 的一次演示） |
| 预算 | $0.1 |
| 验收命令 | `bash -c 'false'` |
| 预期结果 | 失败 |
| 用途 | 证明失败会被如实上报 |

## 这份演示证明了什么、没证明什么

验收命令是 `false`，它在毫秒级返回非零退出码，几乎不消耗成本，也远没花到 $0.1 的预算上限。因此：

- **证明了**：验收失败时，任务被如实判定为失败并上报，退出码与预期一致。即使预算机制完全失效，这条结论也成立。
- **没有证明**：预算能拦住任务。这次运行是被验收失败提前终止的，而不是被预算终止的；没有记录实际花费和停止点，两种情况在结果上不可区分。

要验证「花到上限即停」，需要一个真正跑到接近 $0.1 上限的任务，并记录实际花费与停止位置——这份演示承担不了那个职责。

## 这为什么是一次「失败」的演示

- 任务被验收命令判定失败，这是**设计如此**，不是环境问题，也不是预算触发。
- 不允许为了「让它变绿」而修改验收命令本身，那样演示就失去意义了。

## 花费与停止点的证据在哪

本次运行没有可记录的花费数据：任务在验收这一步就结束了，没有接近预算上限。因此「花了多少、停在哪一步、还差什么」这三项证据由运行报告（该次演示的任务报告／PR 描述）承担，本文件不作转述；真正耗尽预算的运行，其报告必须写清这三项。

## 和正常任务的区别

正常任务的目标是「测试跑通、PR 可合并」；演示任务的目标是「失败能被如实报告、结果可复现」。两者都要求同一件事：**报告不修饰**。
