# 预算：按整条任务累计（重试不重置）

「有成本上限」这条约束见 README「设计约束」，原文是「单次任务的时间、token、执行次数都要封顶」。这里容易读错的是「单次任务」——它指**整条任务**，不是每一次尝试。本文说明实际口径：**预算是整条任务的生命周期额度，每一次尝试都从同一份额度里扣。**

## 口径

一次任务可能包含多次尝试：跑失败了改一版再跑、用例不稳定重跑、环境不对换环境重来。
这些尝试**共用**一份预算，不是各自重新领一份。

- 预算是**三个互不相加的独立计数器**，各自有上限：`token`、`实际耗时（分钟）`、`用例执行次数`。
  - **用例执行次数**的计数单位是「一条用例跑一次算一次」：同一条用例按 `runner.repeat` 跑 N 次，就计 N 次。所以一轮 3 条用例、`repeat = 3`，是 9 次。
- 它们量纲不同，不做换算、也不合并成一个标量。
- 三个上限在任务开始时确定一次，例如 `token 40,000` / `60 分钟` / `120 次执行`。
- 每次尝试结束，把这次尝试的真实消耗分别累加进三个计数器，单位就是上面写的那三个。
- 超限停下不是失败，是这条约束在正常工作。

重试不会让任何一个上限变大。**唯一能让预算变大的，是任务开始时给一个更大的上限。**

## 这些上限从哪来

上限有两个来源，别混在一起（字段与校验规则见 [config.md](config.md)）：

| 上限 | 来源 |
|---|---|
| 时间 | 仓库配置 `limits.maxWallMs` |
| 执行次数 | 由仓库配置推导：`limits.maxCases` × `runner.repeat`（不是配置字段） |
| token / 金额 | **不在仓库配置里**：发起任务时由调用方给定，随任务参数传入；单条用例的消耗另受 `limits.maxSteps` 约束 |

两点容易踩错：

- `limits` 只认 `maxCases` / `maxWallMs` / `maxSteps` 三个字段，**没有** `maxTokens`，也没有金额字段。照「token 上限 40,000」去写 `limits.maxTokens`，配置校验会直接拒绝（见 `src/config.mjs` 的 `LIMITS_KEYS`）。预算走任务参数而不是仓库配置：上限该由发起者定，被测试仓库不能给自己放宽，同一份配置也能在不同预算下复用。
- 「执行次数上限 = `maxCases` × `runner.repeat`」是**配置推导**，和「三个计数器之间不折算」不矛盾：前者回答「额度从哪来」，后者回答「三个额度怎么记账」。别把推导当成折算。

## 两种停止模式

下面两种都算「被预算拦住」，报告里的标签统一，不要混：

1. **触顶**：任一计数器到达上限，任务立即停止——不再生成下一版用例、不再重试，直接给报告。
2. **预估不足未启动**：下一次尝试开始前先估成本，预估消耗超过剩余额度就不启动，任务就此停下。

第 2 种是先算再跑，不是先跑起来撞墙。注意两种情况下**剩余额度都可能大于 0**，所以报告里不能一律写成「预算耗尽」。

## 与 flaky 归因的优先级

README 要求「flaky 先归因再上报：同一个用例重跑若干次，只有稳定失败才算失败」。预算停下时，归因可能还没跑完，两条规则会撞车。优先级写死为**预算优先**：

- 预算一到就停止重跑，不因为「还差两次就能确认」而续跑。
- 没跑够归因次数的用例，在报告里单独标为**「未归因（预算受限）」**。
- 「未归因」既不得计入「稳定失败」，也不得计入「通过」；它是一类独立结论。
- 不得为了跑完归因而自行放宽、拆分或重置预算。

## 例子：token 上限 40,000，第 4 次尝试没有启动

> 下表是**假设示例**：数字是为了说明口径编的，不是真实运行数据。真实运行里「花了多少、停在哪一步、还差什么」由运行报告承担（同一要求见 [money-budget-demo.md](money-budget-demo.md)）。

配置：`maxCases = 40`、`runner.repeat = 3`，所以执行次数上限 = 40 × 3 = 120 次；耗时上限 60 分钟；token 预算由调用方给 40,000。

| 尝试 | 做了什么 | 本次消耗（token） | 累计已用（token） | 剩余（token） | 结果 |
|---|---|---|---|---|---|
| 1 | 读代码 + 生成 3 条用例 | 16,100 | 16,100 | 23,900 | 3 条用例，1 条失败 |
| 2 | 按失败信息改用例再跑 | 9,400 | 25,500 | 14,500 | 全部通过 |
| 3 | 重跑确认不是 flaky | 8,200 | 33,700 | 6,300 | 稳定通过 |
| 4 | 补充边界用例（更大范围） | 未启动（预估 7,100 > 剩余 6,300） | 33,700 | 6,300 | 未执行 |

三次尝试都是 3 条用例、每例 `repeat = 3`，所以执行次数 = 3 条 × 3 次 × 3 轮 = 27 / 120 次；耗时累计 33 / 60 分钟。
第 4 次尝试在开跑前就估出成本超过剩余额度，因此没有启动——这是上面第二种停止模式，**不是** token 触顶。

报告里写的是：

- token 33,700 / 40,000（耗时 33 / 60 分钟，执行 27 / 120 次），剩余 6,300（15.75%）
- 完成 3 次尝试；第 4 次在启动前因预估成本超过剩余额度而未启动
- 已确定的结论（前 3 次）照常给出；未完成的部分写明「因预算受限未覆盖」
- 若有用例没跑够归因次数，另列「未归因（预算受限）」，不并入失败或通过

## 常见误解

| 误解 | 实际 |
|---|---|
| 「失败了重跑一次，预算重置」 | 不重置。重跑继续扣同一份额度。 |
| 「40,000 是每次尝试的上限」 | 不是。40,000 是整条任务所有尝试加起来的上限。 |
| 「token 还剩很多，时间超了也能接着跑」 | 不能。三个计数器任一触顶即停，不看别的还剩多少。 |
| 「token 和秒、次数可以互相折算」 | 不折算。三个计数器各自记账、各自封顶。 |
| 「还剩 15% 的额度，说明是耗尽才停的」 | 不一定。预估不足的尝试根本不会启动，停下时余额可以大于 0。 |
| 「重跑次数不够，但已经通过了，就算通过」 | 不算。没跑够归因次数的一律标「未归因」。 |
| 「额度用完了应该自动放宽，先把活干完」 | 不放宽。自动放宽等于没有上限。 |
| 「超限 = 任务失败，重开一个任务」 | 重开就是新任务、新额度，需要人明确决定，不能由工具自己发起。 |

## 为什么这样算

如果预算按「每次尝试」计，重试就是免费的，工具可以用无穷多次失败的尝试去逼近一个通过的结果——
而这恰好是这条约束要防的事：无限试错会把成本推到不可预期，也会把「跑通了」变成「碰巧跑通了」。

把每次尝试都算进同一份额度，重试就有了价格。工具因此必须先想清楚再跑，而不是先跑再改。
