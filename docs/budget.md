# 预算：累计制

这条规则对应 README「设计约束」里的最后一条：**有成本上限**。

## 一句话

预算按**累计**算，不按单次算。

## 累计在什么之上

累计的载体是**一个任务**：既不是单次尝试，也不是整个会话。

- **起算**：任务第一次尝试。
- **记账**：任务内每一次尝试（含失败重试）都记在同一本账上。
- **清零**：任务结束即清零——跑通、超限放弃、人工收工，都算结束。
- **不共享**：同一会话里的下一个任务是新账，不继承上一个任务的余额。

## 为什么是累计

如果只封顶「单次尝试」，那么一个永远跑不通的任务可以无限重试：每次都在上限内，总量却早已失控。真正要防的不是某一次花得多，而是**在不断重试里慢慢把钱烧完**。

所以在一个任务里，每发生一次尝试，就从该任务的预算里扣一次：

| 尝试 | 本次消耗 | 累计消耗 | 剩余（预算 2000） |
|---|---|---|---|
| 第 1 次 | 700 | 700 | 1300 |
| 第 2 次（失败重试） | 600 | 1300 | 700 |
| 第 3 次（失败重试） | 800 | 2100 | **超限，停** |

上表把三个维度合成一个数字，只为演示累计的过程。实际记账时时间、token、执行次数**各自独立累计、各自封顶**，不互相折算、也不能拿一维的余额抵另一维：任一维度先触顶就停（例如 token 还剩不少，但执行次数到线，一样要停）。

关键点：

- **失败不退预算**。失败的尝试一样花了时间和 token，一样计入累计。
- **重试不是免费的**。重试要重新读上下文、重新跑，成本往往比第一次更高。
- **到线即停**。任一维度累计触顶后不再发起新的尝试，直接收尾并报告。

## 超限之后

不做「再试最后一次」。超限时输出：

- 每个维度各自的累计消耗与上限（时间、token、执行次数分别列出）；
- 停在第几次尝试、当时在做什么；
- 已有的中间结果（哪些用例跑通了、哪些失败了及证据）。

这些信息交给人工判断是加预算还是收工——工具不替人做这个决定，也不在超限后继续试错。

## 与 flaky 归因的关系

README 要求 flaky 用例「重跑若干次」才能归因，重跑同样要花钱。两条规则叠加时的边界：

- **重跑照常记账**。为归因而做的重跑计入执行次数与累计消耗，不因为「这是归因」而免费。
- **触顶就标未归因**。归因所需的重跑如果到达上限，该用例标记为**未归因**，随超限报告一并上报，不静默丢弃、也不默认算作失败。
- **不放宽上限去凑次数**。不允许为了凑够重跑次数临时抬高上限；要更多次数得由人显式加预算。
